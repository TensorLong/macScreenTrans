# 三指查词无法对齐系统问题 — 2026-05-25

## 背景
v0.2.4 已经能在所有主流原生应用(Chrome / Safari / TextEdit / Notes / Mail / Finder /
Terminal.app 等)正常识别光标下的单词,但在 **Zed**、**Ghostty** 类 GPU 自绘应用里
始终失败,即使 Apple 系统的三指查词功能在这些应用里能正常触发。

用户提出关键疑问:**"为什么系统能直接识别,而我们用 AX 不行?我们的实现方式和系统是不是没对齐?"**

原本的两层方案设想:
1. 我们的触发方式跟系统保持一模一样(三指轻点)
2. 当这种方式不能触发时,我们再推到 OCR

但实测发现:**系统在 Zed/Ghostty 中能触发查词,我们用 AX 完全拿不到文本。**
也就是说,我们和系统的实现并不是同一条路径。这次调研就是搞清楚两条路径的差异。

## 调研过程
派三个并行子代理分头调查:
- Agent A: macOS 三指查词的底层调用链
- Agent B: Zed 源码中如何响应系统查词
- Agent C: Ghostty 源码中如何响应系统查词

三个 agent 独立得出**完全一致**的结论。

## 结论:Apple 三指查词走的是 `NSTextInputClient`,不是 AX

### 完整调用链(根据 Zed crash issue #22939 的 stack trace 重建)

```
HID 三指轻点                                                  [硬件]
   ↓
WindowServer 派 NSEventTypeQuickLook (macOS 10.8+)            [系统]
   ↓
[NSResponder quickLookWithEvent:]                             [AppKit]
   ↓
TSMProcessMouseEventWithCompletionHandler                     [TSM Mach 服务]
   ↓
IMKInputSession_Modern handleEvent:completionHandler:         [IMK]
   ↓
[NSTextInputContext characterIndexForPoint:completionHandler:]
   ↓
[<焦点 view> characterIndexForPoint:]                         ← 进程内回调
   ↓
[view attributedSubstring(forProposedRange:)]                 ← 拿到那个词
   ↓
[NSView showDefinition:atPoint:]                              ← 弹定义气泡
```

**这整条链是在目标 app 的进程内部走的**——通过 TSM/IMK 子系统反向回调到 view
自己的 `NSTextInputClient` 协议方法。

### 关键证据

| App | 源码位置 | 关键代码 |
|---|---|---|
| **Ghostty** | `macos/Sources/Ghostty/Surface View/SurfaceView_AppKit.swift:1849` | `extension Ghostty.SurfaceView: NSTextInputClient` |
| **Ghostty** | 同上 L1483 | `override func quickLook(with event: NSEvent)` → `ghostty_surface_quicklook_word` + `self.showDefinition(for: str, at: pt)` |
| **Zed** | `crates/gpui_macos/src/window.rs:236` | `decl.add_protocol(Protocol::get("NSTextInputClient").unwrap())` |
| **Zed** | 同上 L289 | `characterIndexForPoint:` 实现(2025-01 才补,补之前 Apple 查词会直接 crash,见 issue #22939) |

两个 app 都**在自己进程内**实现了 `NSTextInputClient` 协议(IME / 中文输入 / 死键
也都依赖这个协议)。系统通过 TSM/IMK 反向调到这些方法时,**调用发生在 app 自己的
进程里**,所以能拿到精确字符索引和字形矩形。

## 为什么我们做不了

| 尝试 | 结果 |
|---|---|
| 走 `NSTextInputClient` | ❌ 协议是**进程内** AppKit delegate,跨进程不可达 |
| 走 `AXUIElementCopyAttributeValue` 拿 NSTextInputClient | ❌ AX 不暴露该协议 |
| 走某个 `_AX*` 私有 SPI | ❌ 三个独立调研都没发现任何这样的属性 |
| 合成三指轻点 `CGEvent` | ❌ 系统会在目标 app 弹自己的浮窗,**文字无法回传到我们进程** |
| Mach 服务直接调 TSM | ❌ TSM/IMK 端口对第三方不可达,只对 WindowServer 开放 |
| Dictionary Services (DCS) | ❌ 需要先拿到光标位置对应的词,本身不解决定位问题 |
| 注入到目标进程读 view | ❌ 需要 hardened-runtime 豁免 / `DYLD_INSERT_LIBRARIES`,无法签名分发 |
| NSServicesMenuRequestor | ❌ 仅对**已选中**文字生效,不解决光标下识词 |

**Apple 有意把 TSM/IMK 通道封死给第三方。**这不是技术疏漏,是设计决定。

## 业界佐证
工业级查词工具 PopClip、EuDic、Easydict、Bob 多年来均**无法**在 Zed / Ghostty /
Warp / Kitty / Alacritty 这类 GPU 自绘 app 中复刻 Apple 的 Look Up。它们都最终
降级到三选一:
1. AX 选区(需用户先选中)
2. 合成 Cmd+C 抓剪贴板(需用户先选中)
3. **OCR**(屏幕录制权限)

## 决定

1. **v0.2.4 的 AX 实现已经到顶**——主流原生应用全覆盖,无更多空间。
2. **Zed / Ghostty / Warp / Kitty / Alacritty / Figma 等 GPU app 必须用 OCR 兜底**——
   `AXUIElementCopyElementAtPosition` 拿到的就是 `AXWindow` 这种顶层容器,
   下面没有任何文本接口可用。
3. **跳过 Layer 1(AX BoundsForRange 暴力扫)**——只能救少数边缘 AppKit 控件,
   救不了用户实际报的痛点应用,投入产出比低。
4. **OCR(macOS Vision `VNRecognizeTextRequest`)作为下一阶段独立 milestone。**
5. **先把 v0.2.4 现有体验在能识别的应用里打磨好**,在 solid structure 之上再加 OCR。
